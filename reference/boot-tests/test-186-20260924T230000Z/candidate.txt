## What to watch for, and what each outcome means

Run `GTS9_ALLOW_POWER=1 reference/boot-tests/test-186-*/rpmh-stall-capture.sh 5`
and read `rounds/round-N.txt`:

* `verdict=rpmh-timeout-captured` with a `ring_summary` saying the request was
  programmed but never completed → the TCS/RSC/IRQ layer is the next target;
* `ring_summary` saying the completion was seen, but `rpmh_write_batch()` still
  timed out → the completion/lifetime layer is the next target (and watch for
  `LATE COMPLETION`, which would confirm the hazard the source comments warn
  about);
* `holder_tcs=-1` / no matching send → the request never reached programming;
* any anomaly whose monotonic timestamp is earlier than `gts9-rpmh: TIMEOUT` →
  RPMh is a **victim**: follow that anomaly instead;
* `verdict=not-reproduced` → record it as such; do not change code, do not add
  instrumentation, and do not claim a fix.

## Rollback

* Flashing back: `reference/boot-tests/test-183-*/rollback.sh` (known-good pair
  `822ca9dc…` + `3c88b36b…`), or reflash the current profile pair
  (`boot 2e8a693f…` + `vendor_boot f1f4ccf7…` for profile D, `123f35f2…` for
  profile A). The pre-flash images are pulled back to
  `/home/ms/Samsung/gts9-flash-tests/<test>-*/` by the flash script.
* Kernel: rebuild without `GTS9_RPMH_DEBUG=1`; the default patch queue does not
  contain patch 0021, so a plain `scripts/prepare-kernel.sh` + build reverts it.
* The diagnostic is inert without `gts9_rpmh_debug=1` on the command line, so a
  candidate kernel can also be left flashed while booting a profile without it.
