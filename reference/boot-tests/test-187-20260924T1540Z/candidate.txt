# test-187 candidate — built and verified, NOT flashed

Four bundles assembled and validated locally. **Nothing was written to the
tablet.** The safety rule for this phase is that flashing and power actions need
explicit authorisation, and this round stops at *candidate ready for physical
test*.

## Why this candidate exists

The X710 kernel never had `CONFIG_QCOM_AOSS_QMP`, so no driver bound to
`power-management@c300000`, `qmp_get()` deferred forever, and
`a6xx_gmu_acd_probe()` aborted with `-EINVAL`. Measured on the device before
this candidate:

```
gpu_bound=0  gmu_bound=0  aoss_bound=0  deferred=8
```

`3d00000.gpu` has never bound to a driver. See
`docs/GPU_GMU_RPMH_STALL_PLAN.md` and `docs/X710_X910_GPU_RPMH_DIFF.md`.

**These bundles are frozen artifacts of one build, not reproducible outputs.** A
clean rebuild of the same source and config produces a different `Image.gz`,
because `CONFIG_MODULE_SIG_KEY="certs/signing_key.pem"` is regenerated by a
`FORCE` rule on every build. That is a real, separate defect analysed in
`docs/BUILD_REPRODUCIBILITY.md` — and it was observed *live* while preparing this
candidate: the round-1 bundles were built from `Image.gz 2e10d16a…`, a clean
verification rebuild produced `c825426b…`, and **all five bundles were then
rebuilt from the single current build** so they are mutually consistent again.

Each bundle's `BUNDLE_INFO` records the build it came from, and all five now read
`image_gz_sha256=c825426bd7e06f16c6e9e7fd46a2605acfa0cd1e9747789eed403afaacce90ca`,
which matches `out/kernel-gts9wifi/Image.gz`.

**Operational consequence for the operator: do not rebuild between flashing
profiles.** The bundles are consistent with each other and with the current
`out/kernel-gts9wifi`; a rebuild would silently produce a different kernel and
invalidate the A/B. Flash from `out/boot-bundle-test187-*` as they stand.

That kernel contains, in order:

1. `0001`, `0002`, `0003`, `0004`, `0006`, `nxp-ptn3222-…` — the existing queue;
2. **`0007-drm-msm-adreno-a6xx-mark-cxpd-device-link-stateless.patch`** — new,
   the upstream GMU cxpd `DL_FLAG_STATELESS` fix;
3. **`CONFIG_QCOM_AOSS_QMP=y`** — new, the config fix;
4. `diagnostic/0021-…` with the new `rsc_id` field — compiled in, inert unless

| **G** late deferred | `304f0c7355528f4d93594d3b2fb33a36cbcf5e96bc6082961069897db84bde9d` | A + `deferred_probe_timeout=300` |

Profile **G** is new in round 2 and is the most decisive single test available.
The four recorded stalls all begin in the 13.3-14.3 s window, and a real capture
(`test-181-*/host-captures/r3-shutdown-window.log`, 14.3076-14.3127 s) shows that
window **is** the `deferred_probe_timeout` burst: at `late_initcall + 10 s` the
kernel re-probes every deferred device and walks `sync_state` across the whole
clock/interconnect/power-domain graph at once. That same dump names the GPU and
GMU as the reason `gcc`/`gpucc`/interconnect can never finish `sync_state`:

```
qnoc-sm8550 interconnect-1: sync_state() pending due to 3d00000.gpu
gcc-sm8550 100000.clock-controller: sync_state() pending due to 3d6a000.gmu
gpu_cc-sm8550 3d90000.clock-controller: sync_state() pending due to 3d6a000.gmu
```

G moves that burst to ~304 s while leaving every deferred device — GPU included —
exactly as broken as in A. So:

* if the stall follows the timer, **the burst is the trigger**, independent of
  which device is deferred, and the fix direction is "reduce what is pending at
  late_initcall", not "find a driver bug";
* if the stall stays at 13-14 s with no burst there, **the burst is exonerated**
  and the RPMh/RSC direction returns to the front.

`deferred_probe_timeout=0` is *not* the way to test this: `drivers/base/dd.c`
arms the work only `if (driver_deferred_probe_timeout > 0)`, and `= 0`
additionally makes `driver_deferred_probe_check_state()` return `-ETIMEDOUT`
instead of `-EPROBE_DEFER`, changing behaviour for every optional supplier.

Profile D **is** profile A with this kernel: the config fix is in the kernel, not
the command line, so "D" needs no separate bundle. Booting profile A on this
candidate is the D experiment.

## Recommended order

Run **A first**, then **G**, then **B**, then **C**. Do not run them
interleaved: each profile needs its own cold-boot series.

A then G is the highest-value pair, because G is the only profile that attacks the
mechanism of the stall window directly with no code change at all. If A stalls and
G does not, the investigation is essentially solved; if A stalls and G stalls
identically, the burst hypothesis is dead and the RPMh/RSC direction returns.

Before any of it, confirm the flash actually took by checking the profile the
tablet reports. `scripts/stall-ab.sh` does that in its preflight and warns if the
command line does not match the requested profile.

```sh
scripts/stall-ab.sh late-deferred 5    # preflight only, no reboot
GTS9_ALLOW_POWER=1 scripts/stall-ab.sh baseline 5
GTS9_ALLOW_POWER=1 scripts/stall-ab.sh late-deferred 5
GTS9_ALLOW_POWER=1 scripts/stall-ab.sh no-acd 5
GTS9_ALLOW_POWER=1 scripts/stall-ab.sh no-gpu 5
scripts/stall-ab.sh --summary
```

Only the `boot` and `vendor_boot` partitions change between profiles, so an
A→B→C series is two partition writes per step. Profile A's `boot.img` is the
only kernel write in the whole series.

## What to watch for, and what each outcome means

Read `out/stall-ab/<profile>/round-N.txt` and the `--summary` table. Per
`docs/GPU_GMU_RPMH_STALL_PLAN.md` §10, decided in advance:

| observation | conclusion | next step |
|---|---|---|
| A stalls, **B does not** | the ACD requirement is on the causal path and the GPU now binds | fix properly with the config, not by shipping `disable_acd` |
| A stalls, B stalls, **C does not** | GPU/GMU registration is required, but not specifically ACD | profile E on the same kernel |
| **C still stalls** | GPU/GMU is **demoted** — the stall is independent of the adreno driver | stop GPU work; go to E and the RPMh/RSC tree |
| A does not stall at all | "not reproduced this round" | repeat A; do not change code |
| **A stalls, G does not** | the deferred-probe-timeout burst is the trigger, independent of which device is deferred | strongest available result: reduce the pending set at late_initcall (the config fix is the first step) |
| **A and G stall identically** | the burst is exonerated | RPMh/RSC is back in front; run E on this same kernel |
| G stalls at ~304 s instead of ~14 s | the burst is the trigger and the stall **tracks the timer** | confirms the mechanism outright |
| `gpu_bound=1` in A on this kernel | the config fix worked | record it; that alone is a milestone |
| `gpu_bound=0` still, with `aoss_bound=1` | the provider bound but something else blocks the GPU | capture the new first anomaly — it is a different bug |

Two specific things to record that were never measurable before:

* whether `Unable to send ACD state to AOSS` is **gone**;
* whether `Unable to drop a managed device link reference` is **gone** — note
  that patch `0007` is also in this kernel, so a missing WARN cannot be
  attributed to the config fix alone. That is why the WARN's absence is *not* a
  success criterion by itself.

## Rollback

* The flashed pair today is `boot 2e8a693f…` + `vendor_boot f1f4ccf7…`
  (profile D of test-184) or `123f35f2…` (profile A). Both are recorded in
  `docs/NEXT_STALL_DEBUG_PLAN.md` §11.
* `reference/boot-tests/test-183-*/rollback.sh` writes a known-good pair back
  with the verified backup → SHA256 → flash → readback → SHA256 chain.
* Kernel: rebuild from the pinned tree with
  `BUILD_MODULES=0 ./scripts/build-kernel.sh`. To drop the config fix, remove
  `CONFIG_QCOM_AOSS_QMP=y` from `kernel/config/gts9wifi-mainline.fragment`; to
  drop the backport, delete `kernel/patches/0007-*.patch`. `prepare-kernel.sh`
  restores the upstream source on every run, so there is no stale state.
* The RPMh diagnostic is inert without `gts9_rpmh_debug=1`, so profile E's
  kernel can stay flashed while booting A/B/C.

## How this candidate was verified (no device involved)

```sh
GTS9_RPMH_DEBUG=1 BUILD_MODULES=0 ./scripts/build-kernel.sh
```

`Build complete`, exit 0, release `7.2.0-rc3-gts9wifi-dirty`. `prepare-kernel.sh`
logged all seven default-queue patches plus diagnostic `0021` as applied, and
`grep -c 'gts9_rpmh_ev_add\|rsc_id'` on the build worktree's `rpmh-rsc.c` returns
10, which is the proof the diagnostic was compiled in rather than merely present
in the repository. The resolved `out/kernel-gts9wifi/config` contains
`CONFIG_QCOM_AOSS_QMP=y` alongside `CONFIG_MAILBOX=y`, `CONFIG_COMMON_CLK=y` and
`CONFIG_PM=y`.

Bundles were assembled with `scripts/build-boot-bundle.sh` and validated with
`scripts/validate-boot-bundle.sh`: **0 failures** for all four bundle/profile
combinations, including the AVB descriptors, the partition sizes, the empty
platform ramdisk and `SHA256SUMS` verification.

Host checks: `bash -n` over every `scripts/*.sh`, and
`python3 -m unittest discover -s tests -p "test_*.py"` → 244 tests, OK.

A live read-only preflight over the USB shell also succeeded against the
**currently flashed** image and returned the `gpu_bound=0 / gmu_bound=0 /
aoss_bound=0 / deferred=8` evidence quoted above, so the capture path itself is
known to work before the A/B starts.
