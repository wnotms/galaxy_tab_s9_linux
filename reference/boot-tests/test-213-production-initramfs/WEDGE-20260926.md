# The boot that hit the CPU wedge, and what it proved

Boot `03b96f4c-dccb-4b0c-b446-6e340cef1aac` (the one before `6757a9bb`), 2026-09-26.
Reported by the owner as "stuck on the log screen, power key turns the screen off
and on, keyboard does nothing", with a photograph of the panel.

## The photograph is the evidence, and it clears the change that was being tested

The panel showed, in order:

```
GTS9_MINIMAL_STAGE=kernel-userspace
GTS9_MINIMAL_STAGE=waiting-root
GTS9_MINIMAL_STAGE=root-found
GTS9_MINIMAL_STAGE=mounting-root
GTS9_MINIMAL_STAGE=root-mounted
GTS9_MINIMAL_RECORD=/newroot/var/log/gts9-minimal-last-boot
GTS9_MINIMAL_STAGE=init-found
[    1.258665] systemd[1]: Failed to find module 'autofs4'
[    3.297460] [drm:dpu_encoder_helper_wait_for_irq] *ERROR* encoder is disabled
[    3.712532] Bluetooth: hci0: QCA Failed to request file: qca/hpbtfw21.tlv (-2)
[   27.595321] rcu: INFO: rcu_preempt detected stalls on CPUs/tasks:
[   27.595365] rcu: rcu_preempt kthread starved for 2498 jiffies! g=221 f=0x0 RCU_GP_DOING_FQS(6) ->state=0x0 ->cpu=7
[   37.597175] rcu: Unless rcu_preempt kthread gets sufficient CPU time, OOM is now expected behavior.
```

Three things follow directly:

1. **All six handoff stages completed**, and the record was written to the microSD.
   The production initramfs being tested did its job; there is no stage missing and
   no `GTS9_MINIMAL_FAIL`.
2. **`systemd[1]` is running**, so `switch_root` succeeded and Debian was up.
3. The stall is the **documented CPU wedge** - `docs/CPU_WEDGE_EVIDENCE.md` names
   this exact signature (`rcu_preempt detected stalls` + `kthread starved ... ->>cpu=7`)
   and gives it a rate of 1 in 29 boots (3.4 %) on the post-ACD-fix kernel. CPU 7 is
   also the core that logs `cpu cpu7: Voltage update failed freq=3360000` on every
   boot, the X710 3.36 GHz OPP that upstream DT does not declare.

So this boot is the pre-existing wedge, not a regression from the initramfs work -
which is worth stating plainly because it arrived immediately after a flash and the
obvious inference would have been the wrong one.

## Why it did not recover by itself

`docs/CPU_WEDGE_EVIDENCE.md` records an earlier instance of the same wedge that
**did** end on its own, and says why:

> `softlockup_panic=1` fired at 104.3 s and ended the boot. That is the first real
> instance of the profile's `stall → panic → panic=10 → reboot` chain doing its job
> on a wedge.

That profile was a **debug** one. The production profile
(`boot/cmdline.example.txt`) carries neither token:

| token | debug profiles | production |
|---|---|---|
| `panic=` | `10` | **`0`** |
| `softlockup_panic` | `1` | **absent** |
| `workqueue.panic_on_stall_time` | `45` | **absent** |

and the kernel's built-in defaults agree with the production profile:
`CONFIG_BOOTPARAM_SOFTLOCKUP_PANIC=0`, `CONFIG_PANIC_TIMEOUT=0`. So a soft lockup
is detected and reported but never panics, and a panic would never reboot. A wedge
on production is therefore **permanent** until somebody power-cycles the tablet -
which is exactly what was observed: screen alive (the PMIC answers the power key),
userspace frozen, no network, indefinitely.

`panic=0` is deliberate and predates this work: commit `89a6601` ("boot: harden X710
bring-up against console-driven reboot loops") chose it so that a failed
`switch_root` leaves the panic on the screen as evidence rather than rebooting in a
loop. `docs/TWRP_DEBIAN_RECOVERY.md` records both halves of that trade: with
`panic=0` the tablet "hangs with no USB and no key response", with `panic=10` it
"reboots in a loop".

## What this means for the production initramfs

It is a pre-existing trade-off rather than a defect introduced here, and it is not
the initramfs's job: the handoff finished before the wedge began, so no
early-userspace change can prevent or recover this. But it does interact with the
round's goal, which was that a failed boot must not need a key combination:

* the **BCB auto-recovery** handles a *failed handoff* - bad `gts9_rootfs`, missing
  init, a mount that will not complete. It cannot help here, because the handoff
  succeeded and the failure is in the kernel afterwards.
* a **kernel wedge after `switch_root`** is a different failure class, and today it
  ends in exactly the state the owner asked to avoid.

The options, none of them taken in this round because each changes a deliberate
trade-off and deserves its own decision:

1. **`softlockup_panic=1` + `panic=10` on production.** The documented instance
   recovered in about three minutes this way. The cost is the one `89a6601` was
   avoiding: a panic-reboot loop is harder to read than a hung screen, and the panic
   text is lost once the reboot starts.
2. **`softlockup_panic=1` with `panic=0`.** The tablet would still hang, but the
   panel would show the soft-lockup backtrace instead of an RCU message - better
   evidence, same immobility.
3. **`hung_task_panic=1` or a shorter `workqueue.panic_on_stall_time`.** Targets the
   stall rather than the lockup; `docs/CPU_WEDGE_EVIDENCE.md` notes the workqueue
   panic missed by three seconds on the documented instance.
4. **Leave production as it is** and treat a wedge as an accepted 3.4 % risk that
   needs a power cycle. Defensible for a device that is now reachable over ssh and
   whose recovery path is a documented key press.

The honest summary: the failure test from the brief is about a *failed handoff*, and
that is solved. This is the *kernel* failing after a successful handoff, and it is
still unsolved.

And the change that was under test is confirmed on hardware: the boot record is
**792 bytes** with no `cmdline` and no `mmc_devices`, against 1994 bytes before, with
all eight initramfs stages and all eleven `debian_*` fields preserved.
