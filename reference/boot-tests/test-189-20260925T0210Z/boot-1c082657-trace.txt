# boot `1c082657` — the only boot in 89 with a full wedge trace

Extracted 2026-09-25 from the device's own journal (`journalctl -b -67`) on
request; nothing here was produced by a host capture. `1c082657` is a **pre-fix**
boot (it carries `Unable to send ACD state to AOSS`, so the AOSS-QMP/IPCC fix was
not yet in), it is one of the 89 boots the survey covers, and it is the **only**
one of the 89 that printed `frame done timeout` at all.

## What this establishes

**1. Two CPUs stop executing.** `After 10 seconds, these CPUS still haven't
responded to the NMI: 4` and `: 5` is direct evidence at the CPU level, not an
inference from a stalled task. CPU 7, by contrast, answers with an idle
backtrace — so this is not a global freeze.

**2. The stall begins at roughly 7 s, not at 47 s.** Three independent numbers
agree: the journal has no entry between ~7.0 s and 37.2 s; the workqueue pool
reports itself `stuck for 55s` at 62.437 s, i.e. since ~7.4 s; and the RCU grace
period had been failing long enough to be reported at 37.2 s.

**3. The DPU error is a consequence, not the cause — the documented chain is
inverted here.** `docs/DPU_TRACE.md`, `docs/WATCHDOG_X710.md:22` and
`rootfs-overlay/usr/libexec/gts9-power-key.c` all record the order as
"`enc35 frame done timeout` → vblank wait timeout → workqueue lockup". In this
boot the first `enc35 frame done timeout` is at **47.262 s**, roughly **40 s
after** the wedge began. The DPU is doing what a victim does: `kworker/2:2` is
parked in `drm_crtc_wait_one_vblank`, called from `drm_fb_helper_damage_work`, on
a machine whose CPUs 4 and 5 are gone. This is exactly the trap the brief warns
about — the worker that logs last is not the cause — and here it can be shown
rather than asserted.

It does **not** follow that the DPU has no bugs. It follows that in this boot the
DPU messages cannot be read as the origin.

**4. `drm_fb_helper_damage_work` and `vmstat_update` are victims too.** A per-CPU
work item on a CPU that no longer runs anything sits `pending` forever; that is
what `pending: vmstat_update` and the `pwq 18: cpus=4` / `pwq 6,7: cpus=1` stalls
are.

## What this does not establish

* **Why CPUs 4 and 5 stop.** Nothing in this trace names a cause. There is no
  panic, no SError, no PSCI error, no interrupt storm visible in it.
* **That this is the same failure as the 6.2-6.5 s freezes** in the survey. Those
  share the start time and the journal-stops-dead shape, but they reset ~37 s
  later under the external watchdog, before an RCU stall could be reported, so
  their journals contain no equivalent trace.
* **That it still happens.** This boot is pre-fix. Across the 29 post-fix boots
  that reached multi-user, none shows a `frame done timeout`, an RCU stall or a
  workqueue lockup.
