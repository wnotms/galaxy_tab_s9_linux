# test-192 candidate — `loglevel=7` diagnostic command line

**Bundle assembled and validated. NOT flashed.** No partition has been written.

## Why: the console cannot see the marker it is hunting

`After 10 seconds, these CPUS still haven't responded to the NMI: N` is `pr_warn`
(level 4). Every profile here carries `loglevel=4`, which prints levels 0-3. The
failure recovered in round 22 proves the consequence: its pstore console record has
**0** occurrences of that marker, while a journal capture of a wedged boot has 4.
A boot that wedges early leaves no journal, so the console record is the only
evidence - and it was blind by construction.

### Why level 7 rather than 5

5 already captures the `pr_warn` marker and the `NMI backtrace for cpu N` headers.
7 adds the `pr_info` `Sending NMI from CPU x to CPUs y:` line, which names the
*target* CPU - and the target is what the cluster asymmetry is measured from. The
usual objection is a `pr_debug` flood and it does not apply: `CONFIG_DYNAMIC_DEBUG`
is not set, so `pr_debug` compiles away.

## Flash plan

**Flash test-191 first.** This bundle's `boot.img` is test-191's kernel, so flashing
it onto the currently-flashed kernel would be two changes at once.

```sh
# 1. test-191: kernel changes by epss_l3 only, cmdline untouched
reference/boot-tests/test-191-*/flash-profile.sh
# 2. reboot, verify, then test-192: cmdline changes by loglevel only
GTS9_BUNDLE=out/boot-bundle-test192-loglevel \
  reference/boot-tests/test-191-*/flash-profile.sh
# 3. reboot and check
reference/boot-tests/test-192-*/verify-loglevel.sh
```

Changed partitions, both times: `boot` and `vendor_boot` only. Never `dtbo`,
`init_boot`, `vbmeta`, `misc`, `recovery`, `userdata` or the partition table.

## Success criteria

* `verify-loglevel.sh` reports `console_loglevel=7`;
* the console record's first line moves from monotonic ~4.4 s to near 0, and
  level-6 lines appear that were previously absent - the sec-log driver's own
  `gts9wifi-sec-log: persistent console at …` and `Calibrating delay loop …`;
* on the next failure, `gts9-prev-boot-evidence`'s `pstore_*_lines` counters see
  the marker, and `prev_journal=absent-pstore-is-authoritative` is set when the
  failing boot left no journal.

## Failure criteria

* `console_loglevel` is still 4 -> the token did not take; a command-line problem,
  not a kernel one;
* the record still begins mid-boot with only level 0-3 lines -> same;
* a boot that no longer reaches multi-user -> revert `vendor_boot` immediately.

## Observer effect, and the one thing this profile must not be used for

More console output is not free: test-184 showed `/dev/console -> tty0 -> fbcon ->
DRM` backlog can itself make a boot look stalled. **Do not use this profile for
stall-rate counting.** It is a capture profile. `gts9_kmsg_mirror` and
`gts9_dpu_flight` remain off.
