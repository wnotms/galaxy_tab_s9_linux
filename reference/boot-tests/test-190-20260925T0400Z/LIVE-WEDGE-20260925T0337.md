# The live wedge of 2026-09-25 03:37Z, seen from both ends

This is the first time the failure has been observed **while it was happening**, with
the operator watching the tablet and a console capture running. It confirms the
signature from `docs/CPU_WEDGE_EVIDENCE.md` on a live machine, it gives the recovery
time, and it names a concrete new suspect.

## What happened

| time (UTC) | what |
|---|---|
| 03:37:24.107 | the tablet's USB device disappears — the reboot the harness issued |
| 03:37:43.352 | it comes back — **19.2 s outage**, which is what the operator saw as "ten-odd seconds" |
| 03:37:44.221 | its console shows `[FAILED] Failed to start adbd.service - Android Debug Bridge (ADB) daemon.` |
| 03:37:44.251 | `Reached target multi-user.target` |
| 03:37:45.185 | `Started session-1.scope` — **the last thing logged** |
| 03:38:21 | the console capture's own 60 s window ends. Nothing more was recorded. |
| ~03:38:2x | the operator sees the screen **stuck on the log with a blinking cursor, and the keyboard does not respond** |
| 03:40:26 | a probe over COM17 gets `RECV echo ALIVE_$(cut -d" " -f1 /proc/uptime)` and **no result** — echoed, not executed |
| 03:40:5x | the operator sees the login screen come back |
| 03:40:52 | a fresh boot is caught on COM19, reaching multi-user at 03:40:54 |

So the wedge began at ~03:37:45, within a second of the boot completing, and the
machine was back about **three minutes later** — the soft-lockup detector panicking
and `panic=10` restarting it.

## Why it confirms the documented signature rather than adding a new one

* **echo without execution.** `scripts/console-run.sh` sent a command whose output it
  requires, and received the *echo* of the command line and nothing else. That is
  exactly the stall state `test-187/on-device/STALL-SIGNATURE.md` describes, and
  exactly why every harness here requires a command RESULT rather than an open port.
* **the USB gadget stayed up.** `PRESENCE usb0525:a4a7=True` throughout, and the
  console port opened — so the kernel was alive and servicing USB while userspace was
  not progressing.
* **ssh was dead.** The network path is userspace; it stopped when userspace did.
* **it recovered by itself**, which is the profile's `softlockup_panic=1` →
  `panic=10` chain doing its job — the second real instance of that chain firing on a
  wedge, after `fa0f2151`.

## What it adds: `adbd.service`

The boot that wedged is the one whose console shows

```
03:37:44.212  Started gts9-adbd.service - Android Debug Bridge daemon (gts9 fast debug channel)
03:37:44.221  [FAILED] Failed to start adbd.service - Android Debug Bridge (ADB) daemon.
```

Both units. `gts9-adbd.service` is the one this project ships and it starts fine.
`adbd.service` is **Debian's**, left enabled by installing the package, and it fails
because it runs `adbd-usb-gadget setup`, which creates a *second* gadget at
`/sys/kernel/config/usb_gadget/g1`, mounts FunctionFS, and runs a second `adbd` —
and then cannot bind the UDC, because a UDC binds one gadget at a time and `gts9`
owns it.

That is a **new suspect, not a conclusion**: the same unit failed on the preceding
boot too, and that boot was fine, so it is not sufficient on its own. What it is is a
new, self-inflicted source of USB-gadget and configfs churn at exactly the moment the
wedge strikes — multi-user, 6-7 s in — and it was introduced by this project's own
debug-channel work rather than being a property of the port.

It is now disabled, masked, and the stray `g1` gadget removed
(`docs/FAST_DEBUG_CHANNEL.md`). The hunt running since then is the test: **30 cycles
with the packaged unit masked.** If the wedge rate is unchanged, the churn was
irrelevant; if it goes to zero, this was the trigger.

## Why `adbd.service` cannot be the *primary* cause

It is worth stating before the hunt's result is read either way: **10 of the 11 wedge
boots in the journal are pre-fix boots, from long before `adbd` was installed on this
tablet.** The package arrived in round 17; the wedge is in boots from well before
that, with no `adbd`, no `/dev/usb-ffs`, no second gadget and no `adbd.service`.

So whatever the packaged unit is doing, it cannot be what causes the wedge. At most
it is an *aggravating* factor for the post-fix residual — extra USB-gadget and
configfs churn in the same second the wedge strikes — and that is exactly what the
masked-unit run tests. A clean 30 cycles would show the churn contributes; it would
not show that `adbd` explains the pre-fix 22%.

## The 200 s window is marginal, not comfortable

The live wedge was logged last at 03:37:45 and the machine was back around 03:40:5x,
so the panic that ended it came roughly **180 s** after the wedge began. The hunt's
window starts about 5 s before the reboot is issued and the wedge strikes ~20 s after
that, so 200 s of capture leaves only about 15 s of margin over the observed
recovery. **300 s is the honest number for the next run**; 200 s is what is running,
and a cycle that ends with the tablet gone and no marker should be read as "the
window closed first", not as "no wedge".

## Two things this cost, and what changed because of it

**The capture window was too short.** The harness held COM19 for 60 s. The wedge began
at 03:37:45 and the panic that ended it came roughly three minutes later, so the
stack trace — the whole reason for the hunt — was printed to a port nobody was
holding. The window is now 200 s, which spans a 15 s reboot, the boot, and the
watchdog's own timeout.

**A second run silently overwrote the first run's captures.** Both wrote
`wedge-hunt/cycle-N-console.log`, so the wedged boot's file was replaced before it
was read. It was recovered by copying it out the moment the overlap was noticed, and
it is kept here as `wedge-capture-20260925T0337-wedged-boot.log` — but a harness that
can destroy its own evidence between runs is a harness that will do it again.
