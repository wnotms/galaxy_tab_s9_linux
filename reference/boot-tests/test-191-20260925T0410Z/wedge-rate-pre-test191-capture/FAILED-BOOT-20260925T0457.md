# The failed boot of 2026-09-25T04:57Z: the first capture that is not a CPU wedge

Cycle 6 of the round-21 fast hunt wedged, and the operator saw it happen: the
tablet never reached the login screen, sat on the console log, and rebooted itself.
This is the first failure this project has captured **live, with the panel and the
serial console at the same time**, and it does not look like the failure the rate
table counts.

Everything below is from two artefacts, both preserved here:

| artefact | sha256 |
|---|---|
| `cycle-6-watch.txt` — the COM19 capture, every line host-timestamped | `9b9918e57200ebbb52c5f82d979e53a66096d6d03fecf4b76ee087dcfc84a99f` |
| `panel-20260925T0457-failed-boot.jpg` — the panel, as the operator saw it | `9a65eb4f6772879d1a1b6a377cf8af73c9422d4ec8755894e008e143a0f8b414` |

The panel photo is not decoration. It shows **more than the serial console does**,
for a reason given in §4.

```
04:58:03.414  tablet gone          (watchdog: softlockup_panic + panic=10)
04:58:22.721  tablet back          (boot Y; healthy, and still up)
```

So on this boot:

* the wedge struck **1 ms after** multi-user, at monotonic **~6.8 s**;
* the console then went **silent for 57.3 s**;
* the tablet was away 19.3 s for the recovery reboot, which is an ordinary reboot
  duration — nothing about the reset itself was slow.

**~6.8 s is inside the documented window.** `docs/CPU_WEDGE_EVIDENCE.md` says every
wedge on record struck between 5.4 s and 7.0 s into the boot. This one is the
tenth-plus sample of the same onset time, now with a wall clock attached.

The recovery timing is consistent with the armed profile: soft-lockup threshold
2 x `watchdog_thresh` = 20 s from ~6.8 s, then `softlockup_panic=1`, then
`panic=10`, which predicts a reset at ~37 s; observed 45.5 s. The extra ~9 s is the
panic path itself (all-CPU backtrace, the 45 s workqueue-stall panic is also in
range).

1. **The DPU flood starts at 4.44 s and never stops** — roughly one

2. **`mmc1` is the microSD card, and it is the root filesystem.** At 21.99 s the

   handed a command and the bus did not answer.
3. `Error sending AMC DPD/ADM Reset (-110)` is `-ETIMEDOUT` and appears in no
   driver in the pinned tree (grepped), so it comes from the Pogo MCU path over
   I2C, one more peripheral timing out.

## 3. Why this is not the CPU wedge the rate table counts

`docs/CPU_WEDGE_EVIDENCE.md` defines the failure by an unanswered backtrace request:
a CPU that stops taking ordinary interrupts, evidenced by
`After 10 seconds, these CPUS still haven't responded to the NMI: N`, together with
RCU grace periods that cannot retire their callbacks. **None of that is visible
here.** The panel shows the kernel still running and printing from 4.4 s to 25.6 s,
on CPUs 2 and 7, with no unanswered-NMI line, no RCU stall and no soft-lockup
report inside the panel's window.

What this looks like instead: **peripherals stop completing transfers** —
DPU frame-done events never arrive, the SDHCI controller's command never completes,
the Pogo MCU times out — while the CPU keeps executing. Two of those three are
DMA-heavy (the DPU writes framebuffers, SDHCI uses ADMA), and the third is on I2C.

That is consistent with a shared downstream path degrading rather than with a CPU
being parked, and it points at the same place the round's other findings do:
`docs/DT_PROVIDER_AUDIT.md` found the **CPU/LLCC↔DDR bandwidth monitors**
(`CONFIG_QCOM_ICC_BWMON`) unbuilt, and `docs/A6XX_STALE_RPMH_VOTES.md` found the
**GPU never retracting its RPMh/BCM bandwidth votes**. Both are DDR/interconnect
vote defects.

**That is a hypothesis, and a weaker one than it sounds.** Two peripherals failing
does not identify a shared cause; it could equally be a GIC/interrupt-router
problem, or an interconnect clock/power-domain collapse, or the two failures could
be independent. Nothing here distinguishes those. What the capture *does*
establish is the shape and the timing, which is new.

## 4. Two things this capture proved about the instruments

### The boot left no journal at all

* it is **absent from `journalctl --list-boots`** — the list runs `... c97ee7d7`
  (-1) then `b0237b3d` (0), and boot X is simply not there;
* **no journal file contains either marker**: grepping all 29 files under
  `/var/log/journal/*/` for `Timeout waiting for hardware interrupt` and for
  `enc35 frame done timeout` finds nothing, while a control grep for
  `gts9-debian` finds 25 of 29, so the search itself works;
* consequently `gts9-prev-boot-evidence` cannot see it either: the evidence written
  by boot Y reports `previous_boot_id=c97ee7d7` and `marker_dpu_timeout=0`,
  `marker_mmc_timeout=0`, because `journalctl -b -1` for boot Y is *c97ee7d7*, not
  the boot that actually failed.

**So a boot that wedges at 6.8 s is invisible to every journal-based instrument
this project has**, including the 88-boot survey the rate table is computed from.
The console capture is the only instrument that sees it. That is worth knowing
before reading any rate as complete, and it is a reason to keep both the panel
console and COM19.

### The serial console sees less than the panel

COM19 got exactly **one** DPU line, at 6.755 s, and then nothing for 57 s. The
panel shows the flood continuing to 25.6 s. So after the wedge, kernel console
output stopped reaching `ttyGS1` while `tty0` kept printing — the console whose
driver is a USB gadget is the one that stops, which is also why the panel was the
only place the operator could see anything.

### And a correction to my own harness, found by this boot

Three defects, all of which made the failed cycle look clean:

1. **the presence parser only reads the first transition.** `transitions()` in
   `wedge-rate.sh` takes the first `False` and the first `True` after it, so a
   wedge-and-auto-reboot shows up as one ordinary outage. Cycle 6's watcher log has
   **`gone=2 back=3`** while cycles 1–5 have `gone=1 back=2`. Every other cycle's
   file was checked: only cycle 6 has two outages, and the data was there all along;
2. **`nmi_unanswered` is structurally zero on this channel.** The cmdline carries
   `loglevel=4`, which prints only levels 0–3, and the unanswered-NMI line is
   `pr_warn` — level 4. It can never appear on COM19. The early exit's "zero
   markers" guard therefore does not cover the marker I documented it as covering;
   it does still cover panic, soft lockup, RCU stall and workqueue lockup, which
   are level 3 or lower. The shell-answers probe is the real health check;
3. **the cycle was cut short by the very early exit that was supposed to protect
   it.** `EARLY_MIN_UPTIME=45` had the probe firing at ~04:58:03, within a second
   of the moment the tablet went away. That is coincidence, not causation — the
   boot was already broken at 6.8 s — but it means the harness was probing a
   machine that was already wedged, and a wedge that happens *after* the probe
   would be missed entirely.

All three are fixed or recorded in `wedge-rate.sh` and the docs; the presence check
now reports every transition rather than the first pair.

## 5. What would settle it

* **the raw panel log.** The photo is a photograph of a screen, so its timestamps
  were read by eye. The kernel ring buffer for boot X is gone with the boot, but
  `pstore`/ramoops may hold it: `marker_pstore` fields exist in the evidence
  collector, and the next failure should be checked for a ramoops record;
* **raise the console coverage.** `loglevel=4` on a diagnostic profile suppresses
  exactly the marker the rate table counts. A profile with `loglevel=7` and the
  kmsg mirror left *off* would put warnings on COM19 without the observer effect
  the mirror has;
* **decide DPU vs shared-path.** If the DPU flood from 4.4 s is present in every
  boot of this kernel, it is a standing symptom and not the trigger; five healthy
  cycles had **zero** `frame done timeout` lines and this one had one within 1.5 s
  of multi-user, which is suggestive but far too few samples. The cheap test is a
  pass over the retained journals for how many boots contain the string at all —
  `docs/CPU_WEDGE_EVIDENCE.md` records that `1c082657` was the only boot of 89 that
  printed it.

## 6. What this capture changes about the 88-boot fingerprint

`reference/boot-tests/test-189-*/survey-analysis.txt` classifies the retained boots
by a "freeze fingerprint": **the journal stops 5.5-8.0 s in with no orderly
shutdown.** There are ten of them, and the project has been reading that as *the
system froze at about 7 seconds*. The same survey also reports:

```
every boot that printed a frame done timeout:
  idx=-67 1c082657 dpu=15 acd=1 sd=0 last=357.395s
```

**one boot of 89.** This capture says that number is a race, not a rate. Boot X here
printed the same DPU line at `[6.755336]` onto the panel *and* into the COM19
capture, and it printed twenty more of them afterwards, up to 25.6 s — but it left
no journal at all, so a journal-based survey could never have counted them. Whether
a boot appears in that list depends on whether journald managed one more write
before the failure, not on whether the flood happened.

More importantly, the panel shows the kernel **still running and printing for at
least 19 seconds after the journal and the serial console had both gone quiet**.
So for this boot, "the journal stops at ~7 s" does not mean "the system froze at
~7 s". It means **journald stopped being able to write**, because the root
filesystem is `/dev/mmcblk1p1` on `mmc1` (`8804000.mmc`), and 15 seconds later that
controller reports:

```
mmc1: Timeout waiting for hardware interrupt.
mmc1: sdhci: Int stat: 0x00000000     <- no interrupt status bits at all
mmc1: sdhci: Resp[0]: 0x00000000 ... Resp[3]: 0x00000000
```

A controller handed a command that completes nothing is exactly what stops a
journald write. The ten "freeze fingerprint" boots and the eleven "unanswered NMI"
boots may therefore be **two different failures pooled under one fingerprint**: a
system that froze at 7 s, and a system that lost its root filesystem at 7 s and
limped on, unlogged, until the watchdog ended it.

### What survives, and what does not

* **survives**: the boots with an unanswered-backtrace line are still CPU-level
  events. That line is emitted by the console (`pr_warn`), and `1c082657` has both
  it and RCU stalls, so it is a genuine wedge. Nothing here weakens
  `docs/CPU_WEDGE_EVIDENCE.md` for those boots;
* **does not survive**: the assumption that "journal stops at ~7 s" alone means the
  machine stopped executing. For at least this boot it did not;
* **the sets differ**: 10 freeze-fingerprint boots against 11 NMI boots, which are
  not the same list. The overlap has never been computed, and it now matters.

### The cheap discriminator, and why it was invisible

The console's kernel output on COM19 stops at the same moment as the journal,
because `loglevel=4` prints only levels 0-3 and everything after the break is
`DRM_ERROR`-class or worse, arriving on a console whose *driver* is a USB gadget.
The panel's `tty0` kept printing throughout. So:

* **`loglevel=7` on the diagnostic profile** would put the whole post-break period
  on COM19. The existing profiles pin `loglevel=4`, and that is precisely the
  setting that hides it;
* the panel is not a fallback, it is a **second instrument with different failure
  modes**, and on this boot it was the better one;
* **the rootfs/SD path deserves promotion from "do not pre-implicate" to a named
  suspect.** `MMC timeout` is on that do-not-pre-implicate list for good reason —
  it was never seen before this capture. It has now been seen, twice in the same
  boot, with a register dump that says the controller completed nothing.

### Honest limits

* n = 1 for the panel evidence. One boot in which the kernel outlived its journal
  does not make the other nine the same;
* the ordering "journald stops, therefore storage stopped" is an inference, and a
  weak one in one direction: journald *must* stop when its storage stops, so the
  two are not independent observations;
* the DPU flood may be a symptom of the same underlying break rather than of
  storage — the DPU does its own DMA to DDR, and so does SDHCI;
* nothing here says the microSD card is faulty. The controller's `Int stat` being
  zero is about the *host controller*, not the card, and a marginal card, a clock
  or power-domain problem, or an interconnect collapse all look the same from here.

### What it establishes

1. **The panic is a victim, by construction.** CPU 4 panicked inside
   `kick_all_cpus_sync()` - a synchronous cross-CPU call - after waiting 27 s for
   acknowledgements that never came. The panic reason is
   `softlockup: hung tasks`. CPU 4 was not the fault; it was the first CPU to
   *notice*, and `toggle_allocation_gate` is simply the work item that happened to
   call a cross-CPU primitive. This is the round's "do not blame the worker that
   logs last" rule, now demonstrated rather than asserted.
2. **`SMP: failed to stop secondary CPUs 0,3,6-7`** names the CPUs that were
   unreachable at panic time: **0, 3, 6 and 7** - three of them in the big and
   prime clusters. The RCU stall at 27.7 s independently names **CPU 0**, with
   `q=1690` callbacks queued. These are two independent instruments agreeing.
3. **CPU 7 was alive for the whole flood.** The frame-done timeouts arrive every
   ~1.18 s from 6.755 s to 25.7 s on CPU 7. So the DPU flood is *not* a symptom of
   CPU 7 being wedged; CPU 7 is running a timer and printing for 19 s.
4. **The first two failures are display and storage, not CPU.**
   `encoder is disabled id=35` at 4.436 s is a DRM state error, not a timeout; the
   SDHCI write timeouts at 21.99 s and 32.24 s are on `mmc1`, the root filesystem.
5. **RPMh does fail in this boot**: `[T100] Error sending AMC RPMH requests (-110)`
   at 24.804 s. `-110` is `-ETIMEDOUT`. That string is in **no** file in this
   repository or in the pinned tree, so it comes from Debian userspace (pid 100),
   not from a driver - which makes it a *second* independent RPMh timeout
   observation, and the first from outside the kernel.

### Three corrections to the photograph's reading in section 2

The photograph was read by eye, and three values were wrong. They are corrected
here and the same corrections matter for anyone reading the photo:

| section 2 said | the record says |
|---|---|
| `mmc1: sdhci: Int stat: 0x00000000` "no interrupt status bits at all" | **`Int stat: 0x00000003`** - command-complete and transfer-complete *were* set |
| `Resp[0]: 0x00000000 ... Resp[3]: 0x00000000` "the command never completed" | **`Resp[0]: 0x00000900`, `Resp[3]: 0x00000900`** - the card did answer |
| `Error sending AMC DPD/ADM Reset (-110)` | **`Error sending AMC RPMH requests (-110)`** - an RPMh timeout, not a reset failure |

So section 2's conclusion - "a controller handed a command that completes nothing"
- is **withdrawn**. The real dump is `Cmd: 0x0000193a` (CMD25, WRITE_MULTIPLE_BLOCK),
`Argument: 0x070415e8`, `Timeout: 0x0000000f`, `ADMA Err: 0`, `ADMA Ptr:
0x0000000ffffff218`: **a write to the microSD timed out on the data phase** while the
command phase completed. That is a narrower and more specific fault than the one
claimed, and the second dump at 32.24 s (`Argument: 0x00000000`, `Trn mode: 0x23`)
is a different command.

The lesson is not "the photo was useless" - the photo is what made this boot
findable at all, and it carried the DPU flood and the shape of the failure. It is
that **a photograph of a screen is a pointer, not a source**: read the register
value only from the record.

### The compressed dmesg record cannot be decoded, and that is recorded rather than guessed

`dmesg-ramoops-0.enc.z` is 38% printable with no run of 12 printable characters,
and it is **not** a deflate stream: `zlib_inflate` failed with `Z_DATA_ERROR` in
the kernel, Python raises "incorrect header check", scanning the first 256 bytes at
every offset and window finds no zlib or raw-deflate stream, and no zstd, lz4, gzip,
lzo or xz magic appears anywhere in it. The pinned kernel's pstore supports only
`deflate` and `none`, so a record written by *this* kernel should have decoded.

Two candidate explanations, neither established: the record is one an earlier
kernel (stock Samsung or TWRP) left in the same slot, since ramoops survives across
every boot; or it was corrupted by an interrupted write. Nothing here chooses
between them, and no further progress should be claimed on the dmesg record - the
console record already carries the whole failure.

### The instrument fix, which is the durable half

The reason none of this had ever been seen is a directory. `gts9-prev-boot-evidence`
read `/sys/fs/pstore`, and `systemd-pstore.service` **moves every record to
`/var/lib/systemd/pstore` before that unit runs**. The records were on disk the
whole time, and every verdict the collector ever wrote said `pstore_records=`
(empty). Its header comment even asserted the opposite of the truth - "`/sys/fs/pstore`
is empty (`CONFIG_PSTORE_RAM=y` but no ramoops node)" - when the node is present and
dmesg says `pstore: Registered ramoops as persistent store backend` and
`printk: legacy console [ramoops-1] enabled`.

Fixed in `rootfs-overlay/usr/libexec/gts9-prev-boot-evidence`:

* both directories are searched, `/var/lib/systemd/pstore` first, first copy of a
  name wins;
* the stall markers are counted from the pstore records as well as the journal, and
  reported as `pstore_panic_lines`, `pstore_lockup_lines`, `pstore_rcu_lines`,
  `pstore_dpu_lines`, `pstore_mmc_lines`, `pstore_hung_lines`;
* `prev_journal=absent-pstore-is-authoritative` is written when the failing boot left
  no journal, so an all-zero verdict cannot be misread as "nothing happened".

Verified by running the new logic on the device against the real records: it
collects all three and reports `Kernel panic=1`, `soft lockup=1`, `rcu stall=1`,
`dpu=15`, `mmc=2` - where the old code reported nothing at all. **Every future
failure on this port is now self-documenting.**
