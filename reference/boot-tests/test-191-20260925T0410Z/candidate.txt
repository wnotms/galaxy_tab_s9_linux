# test-191 candidate — `CONFIG_INTERCONNECT_QCOM_OSM_L3=y`

**Status: bundle assembled and validated. NOT flashed.** No partition was written
and no power action was taken. Read `README.md` first for what this does and does
not claim.

## The one-line change

```
kernel/config/gts9wifi-mainline.fragment
+ CONFIG_INTERCONNECT_QCOM_OSM_L3=y
```

Commit `2578838 config: build in the EPSS L3 provider cpu0's third icc path needs`.

With `=y`, `17d90000.interconnect` gets a driver (`osm-l3`), so
`of_icc_get_by_index(cpu0, 2)` resolves, `qcom-cpufreq-hw` probes, all three
clusters get a policy and `schedutil`, the L3 vote is driven from the CPU OPP
bandwidth values, and `gcc-sm8550`'s `sync_state()` loses the
`17d91000.cpufreq` blocker.

## Build provenance

```
GTS9_RPMH_DEBUG=1 BUILD_MODULES=0 ./scripts/build-kernel.sh      # exit 0
```

`GTS9_RPMH_DEBUG=1` is **not** a choice — the currently flashed kernel was built
with it, so omitting it would have made diagnostic `0021` a second variable. Both
builds applied the same seven default-queue patches; this one also applied

```
applying diagnostic 0021-gts9-rpmh-timeout-state-dump.patch
```

`CONFIG_INTERCONNECT_QCOM_OSM_L3=y` is at `out/kernel-gts9wifi/config:7817` and
`osm-l3` is in `modules.builtin`. The resolved config hash is identical to the
pre-change build's, which is the expected result when the only delta is one symbol
that selects nothing.

These bundles are frozen artifacts of one build, not reproducible outputs:
`CONFIG_MODULE_SIG_KEY="certs/signing_key.pem"` is regenerated by a `FORCE` rule
on every build (`docs/BUILD_REPRODUCIBILITY.md`). A clean rebuild of the same
source produces a different `Image.gz` and therefore a different `boot.img`.

## Flash plan

`flash-profile.sh` writes **only** `boot` and `vendor_boot`, and backs up whatever
is there first.

```sh
# tablet in TWRP recovery, adb up
reference/boot-tests/test-191-*/flash-profile.sh

# then a plain reset is enough - the initramfs clears the BCB
/mnt/d/android/platform-tools/adb.exe shell reboot system

# Q1, one boot, read-only:
reference/boot-tests/test-191-*/verify-osm-l3.sh

# Q2, only if Q1 passes:
GTS9_ALLOW_POWER=1 reference/boot-tests/test-191-*/wedge-rate.sh 20
```

Order matters: reboot into the new kernel and run `verify-osm-l3.sh` **first**. If
the provider does not bind there is no point spending 100 minutes on a rate series
for a kernel that did not change anything.

## Expected observations

**Q1 — the provider binds.** The three clusters differ, so the three policies
should differ:

| policy | X910 measured | this board, expected |
|---|---|---|
| little (cpu0-2) | `307–2016 MHz` | same OPP table, same SoC |
| big (cpu3-6) | `499–2803 MHz` | same |
| prime (cpu7) | `595–2956 MHz` | same |

`scaling_governor=schedutil` on all three; an `energy_model` directory per policy;
`deferred` down from 3 to 2 in `/sys/kernel/debug/devices_deferred`; and zero
occurrences of both `Failed to find icc paths` and
`sync_state() pending due to 17d91000.cpufreq` in `dmesg`.

**Q2 — the rate.** Most likely outcome given 1/29 post-fix: this is a real bug fix
that does not change the wedge rate. 20 cycles can only detect a large change.

## Success criteria

* `verify-osm-l3.sh` prints PASS on every line of the Q1 table in `README.md`;
* the tablet stays bootable and reaches multi-user on every cycle;
* `wedge-rate.sh` completes its requested cycles with every cycle's
  `kernel=` field naming the new build and `policies=3`.

## Failure criteria

* `17d90000.interconnect` binds but `17d91000.cpufreq` still does not — then the
  deferral is not path 2 and the config route is exhausted;
* `osm-l3 … error hardware not enabled` — ABL does not enable the EPSS block, the
  provider still does not register, and the fix has to come from the bootloader
  path rather than from Kconfig;
* a boot that no longer reaches multi-user, or a new `systemctl --failed` unit.

None of these is a reason to keep the change out: the change is the same one X910
made, and an unbound CPU-path provider is a defect whether or not it explains the
wedge. They are reasons to stop and re-aim rather than to iterate blindly.

## What is deliberately *not* in this candidate

* no driver patch, no DTS change, no cmdline change — the cmdline is byte-identical
  to the flashed one, so profiles A/B/C of test-187 are untouched;
* no RPMh debug change: `gts9_rpmh_debug` stays off in every profile
  (observer effect), and diagnostic `0021` is compiled in only because the flashed
  kernel has it too;
* no `qcom,sm8550-epss-l3` entry added to `osm_l3_of_match[]`. Upstream's
  `sm8550.dtsi` lists that compatible first and the generic `qcom,epss-l3` second,
  and the driver currently matches only the generic one, selecting
  `epss_l3_l3_vote` (`EPSS_REG_L3_VOTE = 0x90`). That is upstream's current
  behaviour for SM8550 and is not changed here; if the L3 vote turns out to be the
  wrong register, that is a separate, upstream-shaped finding.
