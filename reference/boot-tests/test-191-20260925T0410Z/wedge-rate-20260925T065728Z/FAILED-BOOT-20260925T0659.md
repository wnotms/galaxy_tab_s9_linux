# test-191 wedged on its first warm reboot, with cpufreq working

The cycle-1 boot of the test-191 rate series wedged and the watchdog panicked it.
This is the **third** complete failure record, and the first one taken on a kernel
with the CPU path fixed. It contradicts the round's working hypothesis.

Captured 2026-09-25T06:57–06:59Z. Nothing was flashed during the series.

## What happened, on the boot's own clock

| monotonic | event |
|---|---|
| 4.656 s | `[drm:dpu_encoder_helper_wait_for_irq] *ERROR* encoder is disabled id=35` |
| 7.703 s | `[drm:dpu_encoder_frame_done_timeout] [dpu error]enc35 frame done timeout` |
| 23.007 s | `mmc1: Timeout waiting for hardware interrupt.` + full SDHCI register dump |
| 28.647 s | `rcu: INFO: rcu_preempt detected stalls on CPUs/tasks:` — CPU 5 detected by 7 |
| 33.247 s | `mmc1: Timeout waiting for hardware interrupt.` (second dump) |
| 38.675 s | `rcu: rcu_preempt kthread starved for 7743 jiffies! … ->cpu=5` |
| 39.654 s | `Error sending AMC RPMH requests (-110)` |
| 43.487 s | `mmc1: Timeout waiting for hardware cmd interrupt.` (third dump) |
| 74.757 s | `Kernel panic - not syncing: softlockup: hung tasks`, CPU 7, `Comm: kworker/u32:7`, `Workqueue: events_unbound toggle_allocation_gate` |

The panic's call chain is **the same one already on record**:

```
smp_call_function_many_cond
kick_all_cpus_sync
arch_jump_label_transform_apply
__jump_label_update
jump_label_update
...
watchdog_timer_fn            <- the softlockup fires here, on the reporting CPU
```

## The two clocks disagree, again, and this record shows it directly

The systemd journal for this boot (`a2997452`) contains **1115 lines and stops at
monotonic 7.05 s**, immediately after `Reached target multi-user.target`. The
console record runs to 74.76 s and carries the panic.

That is the cleanest instance yet of the distinction `docs/CPU_WEDGE_EVIDENCE.md`
added in round 23: **"the journal stops" is not "the system froze".** The journal
stopped because journald stopped being scheduled — not because the kernel died.
Anyone reading only the journal would date this failure at 7.05 s and miss the
74.76 s panic entirely.

The second outage is the signature `wedge-rate.sh` counts, and it is why the cycle
is scored as a wedge rather than an unfinished cycle.

## What is established, and what is not

**Established.**

* The kernel was test-191. `7a389436` — the boot before this one — is the boot
  `on-device/RESULT.md` verified: `17d90000.interconnect` bound, `17d91000.cpufreq`
  bound, 3 policies, `schedutil`. It ended **clean-shutdown** and it was the harness
  that ended it. Nothing was flashed in between, and the failing boot's journal
  shows the post-ACD-fix GPU binding:
  `[drm] Initialized msm 1.13.0 for 3d00000.gpu on minor 0`, with
  `Unable to send ACD state to AOSS` count 0.
* The failure shape is the established one — same canary, same chain, same victim
  set (`kick_all_cpus_sync` waiting on CPUs that never ACK).

**Not established.**

* **That the failing boot itself had cpufreq bound.** Its journal carries exactly
  one CPU-path line, `cpu cpu7: failed to update OPP for freq=3360000`, and no
  policy lines. That line is **not** a discriminator: the current healthy boot
  prints the identical message with three working `schedutil` policies. So the
  inference is by elimination — same kernel image, previous boot verified — and it
  is the one link in this chain that would be worth closing directly.
* Which event is causal. The DPU `encoder is disabled` error at 4.656 s precedes
  everything else here, as it does in all three records.
* Whether the `mmc1` timeouts are a cause or a consequence. They are new in the
  sense that they dominate this record, but see below — they are not a clean
  discriminator either.

## What this does to the round's hypothesis

`docs/WEDGE_RATE_DECISION_RULE.md` was committed with three falsifiers, and the
first one has fired:

> **A wedge with `policies=3`.** If a cycle wedges while cpufreq is bound and
> governing, then the missing `epss_l3` provider was not the mechanism, and the
> correlation with the ACD era was.

Subject to the one unclosed link above, that is what this is. The `epss_l3` fix is
still correct, still upstream-correct, and still necessary — it is what gives the
tablet three scaling policies instead of none — but **it does not stop the wedge**.

## Which markers actually separate the three records

| record | `encoder is disabled` | `frame done timeout` | `mmc1: Timeout` | `AMC RPMH` | panic |
|---|---|---|---|---|---|
| 04:57Z | 1 @4.436 s | **15** | 2 | 1 | 1 |
| 06:00Z | 1 @5.284 s | **14** | 1 | 2 | 1 |
| this one | 1 @4.656 s | **1** | **6** | 2 | 1 |

Two corrections to earlier readings fall out of this, and both matter for what to
investigate next.

**The frame-done flood is not the common factor.** 15, 14, and 1. The two records
with a flood and the one without all end the same way, so the flood is a property
of two boots rather than of the failure. It cannot be the trigger.

**`mmc1` and the DPU markers trade off against each other.** The record with 15
frame-done timeouts has 2 `mmc1` timeouts; the record with 1 frame-done timeout has
6. That inverse relationship is what a shared upstream cause looks like, not what a
cause and its consequence look like — a failing SD controller does not suppress
display timeouts. Read together with the measurement below, it says the stable
facts about this failure are narrower than any single record suggests.

**And the one thing identical in all three is not a marker either.** The DPU
reports `encoder is disabled id=35` at 4.4–5.3 s on every boot that went on to
wedge. It also reports it, exactly once and at the same place, on the **healthy**
boot running now:

```
[    4.798040] [drm:dpu_encoder_helper_wait_for_irq] *ERROR* encoder is disabled
             id=35, callback=dpu_encoder_phys_cmd_ctl_start_irq, IRQ=[1, 9]
```

Measured on the current boot at 449 s of uptime:

```
marker_dpu_encoder_disabled=1     <- present, and it means nothing
marker_dpu_frame_timeout=0        <- absent
marker_mmc_timeout=0              <- absent
marker_amc_rpmh=0                 <- absent
```

`docs/DPU_TRACE.md` already says this in its own words: the message
"is noise, not a timeout - which is why it also appears in runs with zero
failures, and why it must not be read as the hang." A round that had read that
section first would not have proposed it as a candidate. Recording it here so the
correction stays next to the claim it corrects.

### What the control actually leaves standing

Against that one healthy boot, the markers split cleanly:

| marker | wedged boots | healthy boot | separates? |
|---|---|---|---|
| `encoder is disabled` | all 3 | **present** | **no** — noise, per `docs/DPU_TRACE.md` |
| `frame done timeout` | 15 / 14 / 1 | **0** | not yet — one control, and the counts span 1 to 15 |
| `mmc1: Timeout` | 2 / 1 / 6 | **0** | not yet — same reason |
| `AMC RPMH` | 1 / 2 / 2 | **0** | not yet — same reason |
| `detected stall`, panic | 1 / 1 / 1 | **0** | downstream, by construction |

So the honest statement is narrower than "none of them separates it": three
markers are **present in every wedge record and absent from the one healthy boot
that has been counted**, and one is confirmed noise. Three out of three is the
reason this is worth measuring properly rather than dismissing — but a single
control cannot distinguish "absent on healthy boots" from "this boot happened not
to print it", and the wedge records themselves range from 1 to 15 occurrences.

That is exactly what `probe_markers` exists to settle: the counts only become
evidence next to a denominator, and until this series ran there was no denominator
at all.

### This is the trap the decision rule warned about

`mmc1` is `8804000.mmc`, the microSD the root filesystem lives on
(`gts9_rootfs=/dev/mmcblk1p1`), so its timeouts dominate this record and invite the
conclusion that storage caused the stall. **Every clean boot of the series is a
control for exactly that claim**, and `wedge-rate.sh` now records both markers per
cycle so the comparison exists. Recording it without that control would be the same
error as the one the 04:57Z analysis caught, where "the journal stops" was read as
"the system froze".
