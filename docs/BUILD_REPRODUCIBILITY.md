# Kernel build reproducibility: the embedded module-signing key

**Status: open. Found while verifying the test-187 candidate; deliberately not
fixed in this round.** Recorded here because it invalidates a verification method
this project relies on, and because the fix changes every published hash and so
must be its own deliberate step.

## The observation

Two `KERNEL_CLEAN=1` builds of the **identical** pinned source with the
**identical** resolved config produce different kernels:

```
run 1  Image.gz  6c5780b58c49fc3555b72a43b7f7030491a3ff0ff4b7fb6753d32156835d785b
run 2  Image.gz  c825426bd7e06f16c6e9e7fd46a2605acfa0cd1e9747789eed403afaacce90ca
```

The resolved config is byte-identical across both runs
(`config 9bd3bd59e53378c4fd2901af8b89c6a5d42cc8a20ecce6979ad0ab69f2519518`), and
both are the same source revision with the same patch queue, so this is not a
config or source difference.

The two decompressed `Image`s are the **same size** (48048640 bytes) and differ
in exactly one region:

```
$ gzip -dc Image.gz > k1 ; gzip -dc Image.gz > k2
$ diff <(strings -n 8 k1) <(strings -n 8 k2)
227565,227566c227565,227566
< 260924154511Z
< 21260831154511Z0.1,0*
---
> 260924155134Z
> 21260831155134Z0.1,0*
227567a227568,227569
> Ry%)e_7L
> tGwvuU
```

The differing strings sit next to
`#Build time autogenerated kernel key`, which is the `CN` of
`certs/default_x509.genkey`.

## Root cause

`CONFIG_MODULE_SIG=y`, `CONFIG_MODULE_SIG_ALL=y` and

```
CONFIG_MODULE_SIG_KEY="certs/signing_key.pem"
```

so the kernel embeds a signing certificate. In `certs/Makefile`:

```make
$(obj)/signing_key.pem: $(obj)/x509.genkey FORCE
	$(call if_changed,gen_key)
```

The prerequisite `FORCE` makes the target **always** considered out of date, so
`cmd_gen_key`

```
openssl req -new -nodes -utf8 -sha3-256 -days 36500 -batch -x509 \
	-config $< -outform PEM -out $@ -keyout $@ -newkey rsa:4096
```

runs on **every** build and generates a fresh random RSA-4096 key each time. The
key, its self-signed certificate's validity timestamps (`260924154511Z` /
`260924155134Z` are the `notBefore`/`notAfter` of the two runs, exactly 23
seconds apart — the two builds) and the resulting signature all land inside
`system_certificates.o`, hence inside `Image`.

So the non-determinism is not a toolchain or timestamp-macro problem: it is a
deliberately regenerated random key.

### Why the existing mitigation does not cover it

`scripts/build-kernel.sh` already handles the usual suspects correctly:

* `KBUILD_BUILD_USER=gts9-mainline` and `KBUILD_BUILD_HOST=reproducible`;
* `SOURCE_DATE_EPOCH` from the pinned tree's commit time, and
  `KBUILD_BUILD_TIMESTAMP` derived from it;
* `printf '0\n' > "$build_dir/.version"`;
* `CCACHE_SLOPPINESS=include_file_ctime,include_file_mtime` with `time_macros`
  **deliberately excluded**, with a comment explaining that including it let
  ccache replay an object compiled with a different `__DATE__`/`__TIME__`.

That last point is the subtle one: excluding `time_macros` stops ccache from
*replaying* a differently-timestamped object, but it cannot help a clean build,
where there is nothing to replay and the key is generated fresh regardless.
ccache was never the mechanism here.

## Why it matters for this project

1. **It breaks hash-based verification.** A clean rebuild can never reproduce a
   published `Image.gz` hash, so "rebuild and compare the SHA-256" is not a valid
   check that a shipped image came from a given revision. The bundles in
   `out/boot-bundle-*` are *internally* consistent (each `BUNDLE_INFO` records
   the `Image.gz` it actually embedded, and the test suite verifies that), but
   they are not *externally* reproducible.
2. `kernel/PROVENANCE.md` and `AGENT.md` require kernel image, DTB, config and
   release string to be hashed in every build, and treat the stock config as
   byte-reproducible. The kernel image is the one artifact that is not.
3. It makes a clean-build A/B unsafe to attribute: two "identical" kernels are
   not bit-identical, so a difference between them cannot be dismissed as noise
   by hash comparison alone. For the current round this does **not** undermine
   the test-187 A/B, because all four bundles share one `boot.img` — the same
   single build, not two builds claimed to be equal.

## Candidate fixes (NOT applied)

| approach | sketch | note |
|---|---|---|
| Ship a fixed key | generate `certs/signing_key.pem` once, keep it out of git, and point `CONFIG_MODULE_SIG_KEY` at that stable path | simplest; the key becomes a build input that must be preserved, and must **not** be committed |
| Pre-seed the generated file | provide `certs/signing_key.pem` in the build directory so the `FORCE` rule's output already exists | still re-runs because of `FORCE`; does not work on its own |
| Disable module signing | `CONFIG_MODULE_SIG=n` | changes security posture and would drop `CONFIG_MODULE_SIG_ALL`; a bigger decision than a reproducibility fix |
| `CONFIG_MODULE_SIG_KEY` to an external PEM | same as the first row but with the key outside `certs/` | fine, and arguably cleaner for a build that is not a distro |

Whichever is chosen must document that the key is a **build input**, must not be
committed to the repository, and must be accompanied by a re-generated bundle
set, because every published `Image.gz` / `boot.img` hash changes.

## What was verified

* `KERNEL_CLEAN=1 BUILD_MODULES=0 GTS9_RPMH_DEBUG=1 scripts/build-kernel.sh`,
  run twice, both `Build complete` exit 0.
* Identical `config` hash across both runs.
* Identical decompressed `Image` size.
* The only differing bytes are the embedded certificate's timestamps and
  signature, adjacent to the `Build time autogenerated kernel key` CN.
* `certs/Makefile`'s `signing_key.pem` rule has the `FORCE` prerequisite.
* `CONFIG_MODULE_SIG_KEY="certs/signing_key.pem"` in the resolved config.
