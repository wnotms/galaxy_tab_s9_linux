## Verdict

**No single controller-level difference plausibly explains a slave that answers under the stock controller driver and never answers under mainline. Yes, real differences exist, but they are of the "bus hygiene / recovery" kind, not the "address phase is generated differently" kind.**

Why, concretely:

1. **The failing transfer is programmed byte-identically in both drivers.** The measured `m_cmd:0x8005400` (test-063, `reference/boot-tests/test-063-20260922T082500Z/README.md`) is `M_CMD0 = (I2C_WRITE(1) << 27) | (0x2a << 9)`, which is exactly what STOCK:2096 + `qcom-geni-se.h:322` would write for the same single-message write. Both use the same `SE_I2C_TX/RX_TRANS_LEN` ordering, the same `STOP_STRETCH = BIT(2)` rule for non-final messages, and the same slave-address field (`GENMASK(15,9)`).
2. **The same controller, at the same rate and with the same pin ownership, completes full transactions at `0x51` under mainline** (hardware context, and the 0x51 session is visible in the mainline test logs). So the SE clock, the pads, the level shifters, the pull-ups and the address/ACK machinery all function under MAIN.
3. **No transfer-time register write is missing that could corrupt the waveform.** The only per-transfer SE-config write MAIN lacks is the vendor's RTL-only `SE_GENI_CFG_REG68` stretch workaround (STOCK:436-463), and the only per-transfer writes STOCK lacks are MAIN's `qcom_geni_i2c_conf()` refresh at the top of every transfer and its SE-DMA FSM resets — the FSM resets exist on both sides (STOCK:2242-2252, MAIN:436-448), and the extra `conf()` refresh makes MAIN *more* conservative, not less.
4. **The bus is electrically idle at every failure** (`geni_ios:0x7`, SDA and SCL high) and `geni_status:0x0` (M_GENI_CMD_ACTIVE clear), so nothing is being held down and the command did complete. That excludes "controller left a line low" as the standing state.
5. **The one nominal-rate difference has already been tested and disproved**: the stock kernel runs this SE at **400 kHz, not 100 kHz** (`qcom,clk-freq-out` absent → driver default `KHz(400)`, STOCK:2468-2470; confirmed by `i2c_geni 89c000.i2c: Bus frequency is set to 400000Hz`, e.g. `reference/boot-tests/test-008-20260921T124907Z/last_kmsg-test008-20260921T125027Z.txt:5733`). Mainline at 400 kHz was test-059 and failed (`reference/boot-tests/test-059-20260922T074500Z/README.md`). **The premise "bus runs at 100 kHz in both cases" is therefore wrong for stock** — worth correcting in the project record, but it does not change the conclusion, because the *slower* rate is the one that fails.

What is left as a controller-level candidate is a pair of differences that can **sustain** a latched slave rather than initiate it: (a) the vendor parks SDA/SCL **off** the QUP at every autosuspend (`pinctrl-1` sleep state), while mainline's DT has no sleep state and leaves the QUP attached to the pins permanently; (b) the vendor has a whole post-error cleanup vocabulary (`FORCE_DEFAULT` restore, `M_GENI_CMD_CANCEL`, `I2C_BUS_CLEAR` + `I2C_STOP_ON_BUS`) that mainline does not implement at all. If the STM32 application latches BERR/BUSY and needs a clean STOP, stock can deliver one on the controller's own initiative and mainline cannot. That is the most plausible controller-side story, and it is what the experiment section targets.

## What the code cannot decide

Whether `SE_HW_PARAM_2` (0xE2C) bit 15 is set on this SE decides whether stock's RTL-only paths (`do_reg68_war_for_rtl_se`, `do_pending_cancel`, `FORCE_DEFAULT` restore) are even live on this board; MAIN never reads the register and no log in `reference/` prints it for `89c000.i2c`. Likewise, whether the SE keeps `GENI_OUTPUT_CTRL = 0x7f` / `GENI_FORCE_DEFAULT = 1` across the wrapper-clock and power transitions is not visible from source. Both are one register read away (experiment 3).

## Cheapest discriminating test on hardware

Run in this order; each one is independent and each one kills a different hypothesis.

### 1. (Top) Vendor-style recovery before the first 0x2a access — "is the slave latched, waiting for a clean STOP?"

Patch MAIN's `geni_i2c_xfer()`/error path (a ~20-line, non-upstreamable debug patch) so that the **first** failed transfer triggers exactly the vendor's cleanup and then **one** retry of the same message:

1. `writel(FORCE_DEFAULT, base + GENI_FORCE_DEFAULT_REG)` (0x20) and re-read `SE_GENI_IOS` (this is `do_pending_cancel()`, i2c-msm-geni.c:625-642);
2. `geni_se_setup_m_cmd(se, I2C_BUS_CLEAR /*6*/, 0)`, wait for `M_CMD_DONE_EN` (stock: i2c-msm-geni.c:578-594);
3. `geni_se_setup_m_cmd(se, I2C_STOP_ON_BUS /*7*/, 0)`, wait for `M_CMD_DONE_EN` (stock: i2c-msm-geni.c:596-610);
4. retry the original read/write once.

*If the retry ACKs*, the application's slave was latched and the controller's absence of any recovery/STOP vocabulary is the causal difference; *if it still NACKs*, the slave is not answering for a slave/client-timing reason (announce-window polarity, test-087) and the controller transfer path is exonerated. Either outcome is decisive, and nothing else in this report produces that separation. Note the honest caveat: stock itself does **not** run this path on this board (`qcom,bus-recovery` is absent), so a positive result would mean "mainline's missing cleanup sustains a fault that stock never creates", not "stock's cleanup is why stock works".

### 2. Park the pins exactly as the vendor kernel does (DT-only)

Give `&i2c15` a sleep state copied from `kalama-pinctrl.dtsi:2064-2075`:

```dts
&i2c15 { pinctrl-names = "default", "sleep"; pinctrl-1 = <&qup_i2c15_sleep>; };
/* function = "gpio"; drive-strength = <2>; bias-disable; pins = gpio72, gpio106 */
```

so `geni_se_resources_off()` physically detaches the QUP from SDA/SCL at every autosuspend, as stock does. Separates "QUP permanently attached to an idle bus" from every other candidate; two-line DTS change, and the pin state can be verified from `pinmux-pins` before touching the MCU.

### 3. Read back the one-shot SE configuration at the first transfer (instrumentation, no functional change)

At the top of `geni_i2c_xfer()` and again in `geni_i2c_err()` print `GENI_OUTPUT_CTRL` (0x24), `GENI_FORCE_DEFAULT_REG` (0x20), `GENI_SER_M_CLK_CFG` (0x48), `SE_I2C_SCL_COUNTERS` (0x278), `GENI_IF_DISABLE_RO` (0x64), `SE_HW_PARAM_2` (0xE2C) and `SE_GENI_M_IRQ_EN` (0x614).

* `0x24 == 0x7f` and `0x20 == 0x1` → the probe-time one-shot programming survived; that hypothesis is dead and row 1's timing concern is closed.
* `0x24 == 0` or `0x20 == 0` → the SE lost the vendor's per-resume re-write; that is a controller-level cause and a one-line fix (re-write both in `geni_i2c_runtime_resume()`).
* `0x64 == 0` confirms FIFO/SE mode on both sides; any other value means stock's whole-register test (i2c-msm-geni.c:674-680) and MAIN's masked test (i2c-qcom-geni.c:1115) would have taken *different* transfer paths — a difference this report currently rates as low risk.
* `0xE2C & BIT(15)` tells you whether all of stock's RTL-only WARs are live on this board at all.
